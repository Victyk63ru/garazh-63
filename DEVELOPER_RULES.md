# GARAZH — DEVELOPER RULES

## 1. Твоя роль

Ты работаешь не как верстальщик отдельных экранов, а как ответственный разработчик приложения «Гараж».

Ты отвечаешь за:
- интерфейс;
- логику приложения;
- маршрутизацию;
- состояние приложения;
- роли пользователей;
- localStorage/session state;
- PWA;
- Service Worker;
- кэширование и обновления;
- мобильный рендеринг;
- качество графических assets;
- пользовательские сценарии;
- отсутствие регрессий;
- подготовку изменений к безопасной публикации.

Любое изменение рассматривай с точки зрения всего приложения, а не только конкретного файла.

---

## 2. Source of truth

Перед любыми изменениями сначала определить источник истины.

Приоритет:

1. Последнее явно утверждённое пользователем решение.
2. APPROVED_INTERFACE_CONCEPT_v2.
3. APPROVED_ICON_SYSTEM_v2.
4. Утверждённые production assets.
5. Текущий код приложения.
6. Старые версии и старые SVG — только если явно требуется история.

Запрещено самостоятельно менять:
- структуру продукта;
- роли;
- смысл экранов;
- фирменный стиль;
- утверждённые изображения;
- названия функций;
- пользовательскую логику

без явного согласования.

Если данных недостаточно — не придумывать.

---

## 3. Mobile first

Основная платформа проверки — реальный мобильный интерфейс.

Минимальная тестовая ширина:
390×844.

Особое внимание:
- Android Chromium;
- touch targets;
- fixed bottom navigation;
- safe areas;
- scrolling;
- переполнения;
- обрезка текста;
- изображения;
- качество иконок;
- масштабирование;
- состояние после reload.

Desktop-проверка не заменяет mobile-проверку.

---

## 4. Роли

В приложении три независимые роли:

- child
- parent
- master

Для каждой роли должны существовать собственные:
- home;
- navigation;
- доступные маршруты;
- действия;
- logout.

Нельзя считать проверку ролей завершённой только потому, что прямой URL работает.

Обязательный regression scenario:

Ребёнок
→ logout
→ Мастер
→ logout
→ Родитель
→ logout
→ Ребёнок.

После каждого входа обязательно проверить:
- session.role;
- URL/hash;
- заголовок экрана;
- нижнее меню;
- контент.

Пользователь одной роли не должен попадать в маршруты другой роли.

---

## 5. State / localStorage

При любых изменениях авторизации, ролей и навигации обязательно проверять:

- state.session;
- state.role;
- localStorage;
- восстановление состояния после reload;
- logout;
- повторный вход другой ролью;
- прямой переход по hash URL.

Не полагаться только на DOM-состояние кнопки.

Визуально выбранная роль и фактическая session.role должны совпадать.

---

## 6. PWA и Service Worker

После изменений app.js, styles.css или production assets обязательно проверить Service Worker.

При каждом опубликованном изменении, которое должно гарантированно прийти на устройства, обновлять версию CACHE.

После обновления проверить:
- старый cache удаляется;
- новый app.js приходит;
- новый styles.css приходит;
- новые assets приходят;
- offline fallback не ломается.

Нельзя считать релиз успешным только по локальному серверу.

---

## 7. Графика и иконки

Запрещено растягивать маленькие PNG и затем считать результат готовым.

Перед использованием растрового asset проверить:
- фактический размер в пикселях;
- реальный размер отображения в CSS;
- device pixel ratio мобильного экрана;
- визуальную резкость.

Если PNG выглядит размытым:
- не применять CSS sharpen/filter;
- не увеличивать плохой исходник;
- взять более качественный утверждённый исходник;
- либо подготовить новый high-resolution export из утверждённого источника.

Нельзя перерисовывать утверждённую графику без согласования.

Любой `<img>` должен быть проверен на:
- существующий путь;
- HTTP 200;
- корректную загрузку;
- отсутствие broken-image placeholder.

---

## 8. Процесс исправления ошибки

Всегда работать в порядке:

1. Воспроизвести проблему.
2. Зафиксировать фактическое поведение.
3. Найти корневую причину.
4. Сделать минимальное исправление.
5. Проверить исходный сценарий.
6. Проверить негативные сценарии.
7. Провести regression test.
8. Проверить console.
9. Проверить network / HTTP >= 400.
10. Только после этого сообщать результат.

Не исправлять проблему методом случайного изменения CSS/JS.

---

## 9. Что означает PASS

Нельзя писать PASS, если проверено только:
- что функция существует;
- что маршрут есть в коде;
- что экран отрендерился;
- что нет syntax error.

PASS означает:
реальный пользовательский сценарий был выполнен кликами от начала до конца и результат соответствует ожидаемому.

В отчёте явно писать, ЧТО именно было выполнено.

---

## 10. Проверка перед PR

Перед каждым PR минимум проверить:

- welcome;
- child;
- parent;
- master;
- переходы между основными экранами;
- back;
- logout;
- role protection;
- reload;
- console errors;
- HTTP >=400;
- broken images;
- mobile 390×844.

При изменениях конкретного функционала добавить отдельный тест этого функционала.

---

## 11. Git workflow

Никогда не работать прямо в main для новой задачи.

Порядок:
main
→ новая отдельная branch
→ изменения
→ тест
→ commit
→ push
→ Draft PR
→ проверка
→ только после отдельного разрешения merge в main.

Никогда самостоятельно не сливать в main без явной команды пользователя.

## 13. Главный принцип

Работающий локальный экран ≠ работающий продукт.

Задача считается выполненной только тогда, когда:
- логика правильная;
- роли не смешиваются;
- мобильный интерфейс работает;
- assets отображаются качественно;
- нет битых ресурсов;
- состояние приложения предсказуемо;
- обновление сможет корректно попасть на реальные устройства.
